# AMI 威胁情报系统 — 现状、能力与优化上线方案（对齐稿）

> 用途：与领导对齐项目现状、后续优化方向与部署上线计划。
> 日期：2026-10-21 · 分支：dev/ami-v1.0

---

## 一、一页概览（30 秒版本）

AMI 是一套**威胁情报自动采集 + LLM 结构化加工 + 攻击知识库 + 多维分析展示**的平台，已跑通"采集 → 解析 → LLM 富集 → 知识沉淀 → 分析展示"全链路，目前在本机单机运行。

- **现状规模**：采集情报 2395 篇，沉淀攻击知识 2235 条，LLM 富集成功率 **84.5%**（2023/2395）
- **本轮迭代**：完成性能优化（聚合接口 14 倍提速）、LLM 失败可标记重跑、疑似重复知识自动检测、安全事件报告模块等 10 项改进
- **主要短板**：采集源未规模化启用（7 个仅 1 个启用）、知识 0 发布（全部草稿，缺发布流转）、系统无登录鉴权、未部署
- **需要的决策**：采集源范围与合规、LLM 预算、服务器资源、上线时间与使用范围

## 二、系统现状

### 2.1 系统定位与架构

```
采集层（RSS/列表页/微信 feed）→ 情报库（intel_report + 原文文件仓库）
    → 流水线（HTML→Markdown→图表抓取 → LLM 结构化抽取，失败降级规则抽取）
    → 攻击知识库（attack_knowledge：手法/工具/基础设施/CVE/恶意软件/组织/行业）
    → 展示层（知识库 / 威胁情报多维度分析 / IOC 检索 / 运营总览 / 事件报告 / 运行日志）
```

技术栈：Go 1.26（chi）+ SQLite（WAL）+ 文件仓库；前端 Vue3 + Element Plus。单二进制即可启动，运维成本低。

### 2.2 当前规模（实测）

| 指标 | 数值 | 说明 |
|---|---|---|
| 采集情报 | 2395 篇 | 含原文 HTML、Markdown、图表证据 |
| LLM 富集成功 | 2023 篇（84.5%） | `llm-v2` 版本标记 |
| LLM 失败（规则兜底） | 331 篇 | 已支持筛选 + 一键批量重跑 |
| 攻击知识 | 2235 条 | 全部为草稿态 |
| 已发布知识 | 0 条 | 缺发布/审核流转（可人工发布） |
| 采集源 | 7 个（启用 1 个） | RSS / 列表页 / 微信 feed 已支持 |
| 模型服务 | 4 个已配置 | 可切换 provider |
| 数据体积 | 7.7 GB | 主要是原文与图片证据 |

### 2.3 已具备能力

1. **自动采集**：定时调度（当前全局 1 小时最小间隔），RSS/列表页/翻页/微信 feed 多类型源；手动导入兜底
2. **流水线加工**：正文提取、Markdown 化、证据图抓取、标题/披露时间解析、质量门槛
3. **LLM 结构化抽取**：ATT&CK 手法、漏洞 CVE、恶意软件（含分类）、工具、基础设施、威胁组织、目标行业、摘要；失败自动降级规则抽取并可批量重跑
4. **知识库管理**：待复核标记、质量评分、人工合并去重、**疑似重复自动检测**（CVE/手法/恶意软件重叠 + 标题相似度）
5. **多维威胁分析**：漏洞利用 / 恶意软件 / 攻击组织 / 攻击工具 / 基础设施 / MITRE 手法六个维度聚合，实体详情含关联知识、拓扑、时间线；CVE 按披露时间倒序
6. **IOC 检索**：从解析产物提取失陷指标支持查询
7. **运维支撑**：运行日志（opslog）、情报重试、流水线任务队列、数据水位自动缓存失效

### 2.4 本轮迭代已完成（详见 `docs/CHANGES-v1.0.md`）

| 类别 | 事项 | 效果 |
|---|---|---|
| 性能 | 聚合接口进程内缓存（按数据水位失效） | 首次 0.96s → 命中 0.07s（约 14 倍） |
| 功能 | LLM 降级标记 + 批量重新抽取 | 331 条失败可分批自动重跑 |
| 功能 | 疑似重复知识检测（写入时 + 全量回扫） | 501 条已标记，详情页一键合并 |
| 新模块 | 安全事件报告（上传/预览/下载） | 数据中心新增独立入口 |
| 修复 | 实体详情、附件下载、SQLite 并发锁 | 稳定性提升 |
| 体验 | 知识库筛选区、侧边栏交互、CVE 排序 | UI 一致性 |
| 工程 | 仓库瘦身 + .gitignore | 减少 8.94 GB |

## 三、现存短板（如实评估）

| # | 短板 | 影响 |
|---|---|---|
| 1 | **采集源未规模化**：7 个源仅 1 个启用，且仅支持分钟级全局间隔，无每源独立时间表（cron 字段未生效） | 情报覆盖面与时效性不足 |
| 2 | **知识 0 发布**：2235 条全为草稿，缺"复核 → 发布"的流程化闭环，知识库价值未对外输出 | 系统产出不可用/不可信 |
| 3 | **无鉴权**：API 与页面均无登录，数据含内部情报 | 上线前必须解决 |
| 4 | **单机 SQLite**：不支持多写、无异地容灾；数据 7.7 GB 且持续增长 | 并发与容灾上限 |
| 5 | **LLM 依赖**：抽取质量依赖模型供应商，331 条失败待重跑有 token 成本；无成本统计 | 运营成本不可见 |
| 6 | **英文情报为主**：抽取结果多为英文原文，无中文化摘要输出 | 使用门槛 |

## 四、优化方案（建议分两期）

> 工作量为单人估算，供对齐时参考调整。

### 第一期（P0，上线前置，约 2~3 周）

| 事项 | 内容 | 工作量 | 收益 |
|---|---|---|---|
| 1. 登录鉴权 | 单管理员账号 + session/JWT，API 全量鉴权 | 2~3 天 | 上线安全底线 |
| 2. 发布流转 | 知识"草稿 → 待复核 → 已发布"状态流 + 批量复核 + 发布列表对外可见 | 3~4 天 | 知识库真正可用 |
| 3. 采集源扩容 | 启用/新增安全厂商源（奇安信、360、Unit42、阿里云先知等），补每源独立调度（激活已有 cron 字段） | 3~4 天 | 情报覆盖与时效 |
| 4. LLM 失败清零 | 331 条分批重跑（每条一次调用，可后台慢慢消化） | 1 天（含观察） | 富集成功率 → 100% |
| 5. 部署打包 | 见第五节，Docker/systemd + Nginx + 备份 | 3~4 天 | 具备上线条件 |

### 第二期（P1，上线后 1~2 月内）

| 事项 | 内容 | 收益 |
|---|---|---|
| 6. 情报中文化摘要 | LLM 输出中文摘要字段，知识库/详情双语展示 | 降低使用门槛 |
| 7. 质量评分升级 | 发布前质量门禁（维度完整度、置信度、来源权威度加权） | 知识可信度 |
| 8. 订阅与告警 | 新 CVE/新组织情报按关键词订阅，站内/邮件/企业微信推送 | 从"看板"变"预警" |
| 9. 成本观测 | LLM token 用量按源/按日统计报表 | 成本可控 |
| 10. 存储升级路径 | 数据量到 50GB+ 时评估迁移 PostgreSQL；文件仓库对象存储化 | 扩展性 |

### 远期可选（P2）

- 多用户与角色（分析员 / 审核员 / 只读）
- 对外只读 API / 周报自动生成（PDF/Word）
- 与内部 SOC/工单系统对接（事件报告联动）

## 五、部署上线方案

### 5.1 部署形态建议

```
内网 Linux 服务器（4C8G 起步，磁盘 100G+）
  ├─ systemd/Docker：ami 后端单二进制（静态资源可内嵌或由 Nginx 托管）
  ├─ Nginx：HTTPS 反代 + 静态资源 + 访问控制（限内网网段）
  └─ 数据目录 /data/ami：SQLite 库 + 文件仓库，定时备份
```

- SQLite 单写模型与当前"单人运营 + 低频查询"匹配，**上线初期不建议引入 PostgreSQL**，降低运维复杂度；预留迁移路径（二期第 10 项）
- 前端构建产物由 Nginx 托管，后端只暴露 `/api`

### 5.2 上线检查清单

1. 服务器申请与网络策略（是否需要访问外网采集源，出站白名单）
2. 登录鉴权上线（P0-1）
3. 域名/证书（内网 HTTPS）
4. 数据初始化：空库上线 or 迁移现有 7.7 GB 数据（建议迁移，保留已有 2235 条知识）
5. 定时备份：SQLite `.backup` + 文件仓库 rsync，每日一次，保留 7 天
6. 健康检查与日志轮转
7. 采集源灰度：先启用 3~5 个源观察一周（反爬、频率、质量），再全量

### 5.3 风险与对策

| 风险 | 对策 |
|---|---|
| 采集源反爬/封禁 | 控制频率（每源独立间隔）、UA 伪装、必要时走代理出口 |
| 情报版权/合规 | 仅内网使用 + 保留原文出处链接；对齐时确认范围 |
| LLM 供应商不稳定 | 已支持多 provider 配置切换，失败自动降级规则抽取 |
| 单机故障 | 每日备份可快速重建；二期评估主备 |

## 六、拉齐关键点

1. **采集源范围与合规**：优先覆盖哪些厂商/行业情报源
2. **LLM 预算**：重跑 331 条 + 日常增量（估计每天 50~100 篇）的 token 成本口径，可接入内部模型
3. **使用范围**：初期给谁用（仅安全团队 / 扩大试读）？是否需要只读账号体系？
4. **发布流程**：知识发布是否需要人工审核岗，还是先自动发布 + 事后复核？
